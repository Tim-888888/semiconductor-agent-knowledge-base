# T9-4.3 通用会话记忆与按需路由设计

## 1. 状态与边界

本文记录已经确认的产品与架构方案。`T9-4.3.1` 通用会话上下文、`T9-4.3.2` 受控意图/按需路由和
`T9-4.3.3a~b` 意图治理、评测与 Few-shot 影子实验已经完成开发与 ECS 验收；`T9-4.3.3c~d` 和 `T9-4.3.4` 仍未开发，
不得把 Few-shot 上线、自然生成、组合执行、专用校验或完整浏览器闭环描述为已经实现。

本次扩展解决两个问题：

1. 同一 `thread_id` 中，Agent 能理解“我刚才问什么了”“继续分析它”等依赖历史的表达。
2. 普通会话、历史回顾和文本处理请求不默认进入 RAG；只有需要受控知识、实时数据或外部资料时，
   才调用对应检索或工具。

本方案复用现有 FastAPI、LangGraph、MongoDB、LLM 网关、T5 检索、制造数据工具和 SSE，不新增
基础设施服务。加入受控多任务、纠正/取消和半导体意图评估后，实现复杂度评估为中高，约 `7/10`，
预计比原 T9-4.3 增加约 `25%~35%` 的开发与测试工作。主要复杂度来自状态一致性、路由边界和回归
验收，不是意图标签本身。为控制复杂度，一期不增加独立向量意图模型、第二次意图 LLM 调用、自由任务
DAG 或新基础设施服务。

## 2. 现状诊断与 T6 边界

当前 `agent_threads.messages` 已持久化用户和助手消息，但现有 Agent 图主要把本轮 `request` 交给
约束提取、检索和回答节点，没有在每轮运行前装配可用的会话历史。因此，“我刚才问什么了”会被当成
一条新的知识问题，并继续进入检索，最终出现空洞或不自然的回答。

T6 已完成的能力保持有效：

- 缺少关键字段时通过 `interrupt()` 暂停，并通过 `Command(resume=...)` 跨实例恢复；
- MongoDB Checkpointer 保存图执行状态；
- T5 证据、制造数据工具、证据账本和答案校验闭环已经通过验收。

T6 的“同一线程可恢复”不等同于“通用连续会话已经实现”。通用历史装配、上下文指代、按需路由和
不同路由的答案校验属于新增的 T9-4.3 范围。

## 3. 总体流程

```text
用户问题
  -> HTTP/JWT 鉴权 + thread 所有权/Scope 检查
  -> ContextAssembler 装配当前线程上下文
  -> 0. 前置闸门：安全、服务范围、风险与禁止操作
  -> L0 确定性快速通道：固定命令、取消/继续、历史引用识别、稳定实体格式
  -> 1. 交互模式 + 一级意图 + 独立情绪信号
  -> 2. task_items：针对什么对象、执行什么任务、任务间有什么受控依赖
  -> 3. 槽位操作与路由建议：设置/继承/纠正/清除，信息是否充分
  -> 风险与置信度安全网
  -> 确定性 RoutePolicy 作最终路由决策
       -> chat_direct（普通会话 / 受历史约束的自然回答）
       -> reuse_evidence
       -> internal_rag
       -> tool_only
       -> rag_and_tool
       -> rag_and_web
       -> clarify
       -> refuse
  -> 路由专用生成与校验
  -> 持久化消息、上下文、摘要、Checkpoint 和审计信息
```

JWT 与线程 ACL 必须在读取历史之前完成。`ContextAssembler` 随后提供最近消息、旧历史摘要、当前调查
对象和上一轮证据引用，前置闸门才能正确判断“继续分析它”是否属于服务范围。问候、历史回顾和会话控制
本身属于系统服务范围，不要求出现半导体关键词。

## 4. 一次理解、确定性决策

三层识别是逻辑分层，不实现为三次串行 LLM 调用：

- 明显的问候、历史引用、拒绝项、固定命令和稳定实体格式优先由 L0 确定性规则处理；L0 只确定语义和
  引用目标，不直接生成僵硬答案；
- 复杂表达只调用一次结构化 LLM 理解，同时返回交互模式、一级意图、任务项、情绪、槽位操作和路由建议；
- LLM 只提出建议，最终路由由可测试的 `RoutePolicy` 决定；
- 低置信度、关键槽位冲突或高风险请求进入 `clarify` 或 `refuse`，不猜测。

这样可以控制延迟和成本，也避免三次分类结果互相矛盾。新增意图、对象、任务、路由和槽位规则分别通过
注册表扩展，避免把所有逻辑堆入一个大型 `if/elif`。

### 4.1 L0 确定性快速通道

L0 仅处理语义绝对明确、误判代价低的输入：

- `/help`、`/new` 等固定命令；
- “停止生成”“取消本次查询”“继续”“放弃本轮追问”；
- “我刚才问什么了”等有精确线程语义的高频短语；
- 经过业务规则确认的 Tool、Lot、Wafer、Alarm Code 等稳定格式。

规则表和必要正则在模块加载时创建一次，不在每个请求内重复编译。一期命令规模很小，使用字典、
`startswith` 和少量预编译正则即可，不引入 Trie。L0 不负责猜测 Recipe 影响分析、异常诊断等复杂意图。
历史回顾命中 L0 后仍进入 `chat_direct` 的历史约束生成：服务端先选择准确 `message_id`，模型只负责
自然复述；模型不可用或输出校验失败时回退到精确消息直答。

### 4.2 受控范围与明确不做项

- 单轮最多识别 `3` 个 `task_item`；超过上限时澄清或请用户拆分。
- 只支持 `RAG`、`Tool`、`RAG + Tool`、`RAG + Web`、`历史处理 + 新任务` 等预定义组合。
- 多意图识别不代表全部自动执行；写操作、越权任务和高风险任务仍拒绝或进入审批。
- 不建立通用任务 DAG，不允许多个自由 Agent 自主扩展任务和依赖。
- 不增加独立向量意图路由；未来只有在真实 Trace 上完成影子评估并证明收益后才重新评审。
- 不采用通用固定置信度阈值，也不因连续低语义置信度关闭 LLM。语义不确定进入澄清；Provider 熔断只由
  超时、429、5xx 等服务故障触发。

## 5. 三层识别模型

### 5.1 交互模式、任务/非任务与一级意图

每轮先识别 `interaction_mode`：

| 交互模式 | 含义 | 示例 |
| --- | --- | --- |
| `task` | 明确要求查询、分析、生成或调用工具 | 查一下 ETCH-03 最近 24 小时报警 |
| `conversation` | 问候、确认、感谢或一般交流 | 谢谢，我明白了 |
| `feedback` | 对答案质量、速度或表达方式反馈 | 回答太复杂了 |
| `control` | 取消、继续、纠正范围或结束任务 | 别查了，取消这次查询 |
| `clarification_answer` | 回答系统上一轮结构化追问 | 产品是 P-ALPHA，时间是昨天 |
| `mixed` | 同一句中同时包含非任务和一个或多个任务 | 你好，顺便查下 ETCH-03 报警 |

`feedback` 不应自动进入投诉或检索流程；`conversation` 也不应因为没有半导体关键词被判为 OOD。
`mixed` 必须保留其中所有有效任务，不能让问候、抱怨或客套话吞掉业务请求。

一级意图使用稳定、数量有限的类别：

| 一级意图 | 含义 | 示例 |
| --- | --- | --- |
| `conversation` | 问候、历史回顾、承接或改写当前对话 | 我刚才问什么了 |
| `knowledge_query` | 查询受控知识或通用领域知识 | 当前 SOP 怎么要求 |
| `investigation` | 对异常或 Case 做调查与诊断 | 这批边缘缺陷可能和什么有关 |
| `data_query` | 查询实时或模拟制造数据 | 查这批 Lot 最近 24 小时 FDC |
| `action_request` | 请求执行工具或受控动作 | 生成检查清单并查询报警 |
| `content_task` | 总结、翻译、改写、比较已有内容 | 把刚才回答说简单一点 |

### 5.2 二级意图与受控多任务

二级意图不维护无限增长的组合标签，而是拆成“对象 + 任务”：

- 对象示例：`previous_message`、`previous_answer`、`SOP`、`Recipe`、`FDC`、`SPC`、
  `wafer_map`、`lot`、`case`。
- 任务示例：`recall`、`summarize`、`simplify`、`lookup`、`compare`、`diagnose`、
  `explain`、`execute`。

例如“把刚才回答简单解释一下”可表示为 `target=previous_answer`、`task=simplify`，无需创建
“历史回答简单解释”这一专用类别。

一句话包含多个任务时输出 `task_items`，最多 3 个。每项包括 `task_id`、一级意图、对象、动作、
必要槽位、允许的受控依赖和执行决策。例如“查 FDC 报警，再对照 SOP 给排查建议”拆为数据查询、
知识查询和依赖前两项的调查任务，`RoutePolicy` 将其合并为一个 `rag_and_tool` 执行计划，而不是启动
三个自由 Agent。

如果用户同时要求“查询报警、修改 Recipe、生成报告”，系统可以执行查询与报告准备，但 Recipe 修改
仍按写操作拒绝或转审批。部分任务失败时，回答必须逐项说明已完成、未执行和失败原因，不得静默丢单。

### 5.3 槽位操作、取消与上下文引用

第三层输出：

- 本轮显式槽位；
- 从当前线程继承的槽位及其来源消息；
- 槽位操作 `set`、`inherit`、`correct`、`clear`；
- 仍缺失的必要槽位；
- 被指代的消息、Case 或证据 ID；
- 独立化后的查询文本 `standalone_query`；
- 建议路由与置信度。

继承 Product、Tool、Chamber、Recipe、时间范围等字段时必须保存来源，不能把模型推断当成用户明确输入。
权限、时间有效性或查询含义可能变化时，系统应重新确认或重新检索。

纠正必须执行依赖失效传播。例如“不是 ETCH-03，是 ETCH-04”会纠正 Tool，并使依赖旧 Tool 的
Chamber、Recipe、证据和复用资格失效，但不会清空无关的 Product 或整个线程。取消必须标明范围：
当前生成、当前任务、指定 `task_id` 或待补充澄清；自然语言“别查了”不能默认删除会话历史。

### 5.4 情绪与任务解耦

情绪只作为辅助信号输出 `sentiment`、`urgency` 和 `complaint_signal`，用于回复语气、信息排序和审计，
不直接决定 RAG、工具或投诉路由。“这个报警太烦了，赶紧帮我查”仍是业务查询；紧急表达不能绕过权限、
审批和证据校验。

### 5.5 意图定义卡与易混淆边界

T9-4.3.3 新增版本化、机器可读的半导体意图定义卡。每张卡至少包含 `handles`、`excludes`、
`confused_with`、正例、困难反例、必要槽位、允许路由和风险级别。定义卡只覆盖稳定业务意图和高混淆
边界，不为所有“对象 x 动作”建立笛卡尔积标签。

首批优先覆盖 SOP 查询与异常调查、FDC 数据查询与报警解释、Recipe 查询与危险写操作、普通聊天与
能力咨询、历史回顾与最新事实查询等混淆对。定义卡同时作为结构化 Prompt、人工标注、错误分析和
离线评估的共同真相；变更必须增加版本并触发意图回归。

一期固定采用“全量卡入 Prompt”：除命中 L0 的确定性请求外，每次结构化 LLM 理解都加载同一目录版本中
全部 `status=active` 的意图卡，不做关键词、Embedding 或另一次 LLM 候选卡预筛。每张卡提供精简但完整的
处理范围、排除范围、混淆关系和少量代表性正反例，使模型始终看见全部合法选项。`draft/deprecated` 卡不得
进入 Prompt；加载器在进程启动时校验并缓存活动目录，运行审计记录目录版本、Hash、活动卡数量和输入
Token，保证结果可复现。L0 历史引用、固定命令和取消仍可绕过该分类调用。

意图卡全量加载与 Few-shot 案例检索是两件事：前者是一期固定策略，后者只决定是否额外提供历史判例。
当活动卡数量、意图 Prompt Token、P95 理解延迟或混淆指标超过预先冻结的容量门禁时，系统只产生告警和
评审任务，不能自动切换候选卡模式；候选卡检索属于未来架构变更，必须单独设计、评测和确认。

## 6. 结构化理解契约

计划新增内部契约 `ConversationUnderstanding`，示例：

```json
{
  "interaction_mode": "conversation",
  "primary_intent": "conversation",
  "task_items": [
    {
      "task_id": "task_1",
      "target_type": "previous_user_message",
      "task": "recall",
      "depends_on": [],
      "execution_policy": "execute"
    }
  ],
  "affect": {
    "sentiment": "neutral",
    "urgency": "normal",
    "complaint_signal": false
  },
  "slot_operations": [],
  "explicit_slots": {},
  "inherited_slots": {},
  "missing_slots": [],
  "context_message_ids": ["msg_xxx"],
  "standalone_query": "",
  "cancel_scope": null,
  "suggested_route": "chat_direct",
  "confidence": 0.99
}
```

所有枚举由 `contracts` 统一管理，`task_items` 最多 3 项。结构化 LLM 输出使用 Provider 支持的 JSON
Schema/工具调用约束；分类调用在 Provider 支持时设置 `temperature=0`。输出必须经过 Pydantic 二次校验，
必要时最多做一次结构化修复重试；仍失败则进入确定性降级，不得把任意模型文本直接解释为路由、数据库
过滤条件或工具参数。严格 Schema 只能约束输出形状，不能替代服务端校验、权限和异常处理。

## 7. 路由策略

| 路由 | 触发条件 | 下游 | 校验重点 |
| --- | --- | --- | --- |
| `chat_direct` | 问候、能力说明、无需外部事实的交流，以及历史回顾/历史回答变换 | 有界会话上下文 + LLM | 历史模式只使用服务端选中的消息 ID；不伪造知识库引用 |
| `reuse_evidence` | 明确承接上一轮且证据仍有效 | 上轮证据账本 | 重新校验 ACL、版本和有效期 |
| `internal_rag` | 需要 SOP/Recipe/Case/手册事实 | T5 检索 | 证据与引用闭合 |
| `tool_only` | 只需要制造数据 | 只读工具 | 参数、权限、时间范围和工具结果 |
| `rag_and_tool` | 需要知识规则与制造数据联合判断 | T5 + 只读工具 | 区分文档事实与实时数据事实 |
| `rag_and_web` | 内部证据不足且满足 Web 白名单策略 | T5 + Web 网关 | 外部来源降级，不覆盖内部受控证据 |
| `clarify` | 关键槽位不足、歧义或低置信度 | `interrupt()` | 不调用检索和工具 |
| `refuse` | 越权、危险、写操作或超出边界 | 拒绝/审批提示 | 不读取或泄露下游数据 |

`RoutePolicy` 只接收已验证的权限、理解结果和上下文元数据。路由优先级至少满足：安全拒绝高于所有
业务路由；历史可回答时使用 `chat_direct` 且不检索；需要最新版本或实时状态时不得复用旧证据；关键
条件不足时先澄清。已有 `history_direct` 枚举在迁移期只用于反序列化旧请求台账和 Trace，新请求不再
产生该路由；待历史数据兼容窗口结束后再单独评估是否移除，不能在本次改动中破坏旧记录。
多个 `task_item` 只能映射到白名单执行组合。`RoutePolicy` 还要输出每个任务的 `execute`、`clarify`、
`refuse` 或 `defer` 决策，保证用户说两件事时不会只处理一件，也不会因为其中一项越权而掩盖其他安全项。

### 7.1 路由专用自然生成

`chat_direct`、`clarify` 和 `refuse` 使用现有流式 LLM 网关生成自然回复，但模型不拥有路由权：

- 普通 `chat_direct` 使用 `ContextAssembler` 提供的有界最近历史、能力说明和当前请求；
- 历史回顾/变换使用服务端选中的 `context_message_ids`，禁止模型自行选择“上一条”；回答必须可由这些
  消息直接支持，校验失败时返回确定性精确内容；
- `clarify` 只围绕结构化 `missing_slots` 和冲突项提问，不新增要求、不提前调用检索或工具；
- `refuse` 使用稳定粗粒度 `reason_code`、能力边界和允许的替代用法生成友好说明，不穷举用户表述，
  不泄露策略细节，也不暗示已执行被拒绝的动作；
- 所有生成沿用真实 SSE Delta；情绪只影响措辞，不能改变权限、任务状态或证据要求。

置信度阈值不写死为通用 `0.8/0.6/0.4`。阈值需按 `interaction_mode`、路由风险和半导体意图评估集
校准；高风险工具和证据复用采用更保守门槛。低语义置信度进入澄清，不触发 session 级 LLM 熔断。

## 8. 会话记忆模型

### 8.1 四类状态边界

| 类型 | 业务真相 | 用途 |
| --- | --- | --- |
| 精确会话消息 | `agent_threads.messages` | 回答“刚才说了什么”、展示和审计 |
| 会话摘要 | `agent_threads.summary` | 压缩较旧历史，帮助长对话理解 |
| 活跃工作上下文 | `agent_threads.active_context` | 当前 Product/Tool/Case/证据等可继承状态 |
| 图执行状态 | `checkpoints` / `checkpoint_writes` | LangGraph 暂停、恢复、重试和步骤回放 |

Checkpoint 不是通用会话记忆，不能代替精确消息和上下文装配。跨线程长期记忆仍只允许用户或管理员
显式批准后写入 `long_term_memories`，不自动把普通聊天、模型猜测或敏感制造内容沉淀为长期事实。

### 8.2 上下文装配

每轮默认装配：

1. 当前用户消息；
2. 最近 `10~12` 轮精确消息；
3. 更早历史的摘要和 `summary_upto_message_id`；
4. 当前活动对象、槽位及来源；
5. 可复用证据 ID、版本、有效期和上一轮 Trace；
6. 经过批准且未过期的用户偏好。

摘要不可覆盖最近精确消息，也不是受控事实来源。“我刚才问什么了”应直接读取精确消息，不让 LLM 从摘要
猜测。上下文超过预算时先压缩旧历史，再限制低优先级内容，不能截断当前问题和关键引用。

## 9. 计划的数据结构变更

以下均为向后兼容的可选字段，实施前仍需编写迁移与回滚方案。

### 9.1 `agent_threads`

- `summary_upto_message_id`：摘要覆盖到哪条消息；
- `context_version`：上下文结构版本；
- `next_turn_seq` 或 `last_turn_seq`：线程内严格递增顺序；
- `active_context`：`topic`、Product、工艺层、Tool、Chamber、Recipe、时间范围、Case/Lot、
  `evidence_refs`、`trace_id`、更新时间；
- `messages[].turn_seq`：消息稳定排序和并发对账；
- 现有 `summary`、`messages`、`clarification_round` 和 `pending_fields` 保留。

### 9.2 `agent_message_requests`

计划补充：

- `route_decision`、`route_confidence`；
- `interaction_mode`、`task_items` 和每项执行决策；
- `context_message_ids`、`standalone_query`；
- `retrieval_skipped_reason`；
- 继承槽位及来源的脱敏摘要；
- `slot_operations`、`invalidated_context_refs`、`cancel_scope`；
- 情绪辅助信号的脱敏枚举，不保存额外敏感原文；
- 路由阶段、耗时和稳定错误码。

不保存隐藏思维过程、系统 Prompt、密钥或未经授权的完整证据。Trace 只记录可解释的输入、规则、候选和
决策结果。

## 10. 一致性、安全与并发

- 同一线程只允许一个活动消息请求；后到请求应排队或返回稳定冲突状态，避免消息和摘要乱序。
- 用户消息、最终助手消息、请求台账和上下文更新必须可幂等对账；取消或失败不保存半截助手答案。
- 复用上一轮证据前重新检查用户 Scope、文档审批状态、版本、生效期和图片权限；失效时重新检索。
- 新线程不得继承旧线程的短期消息或活动上下文；跨线程只加载显式批准的长期记忆。
- `standalone_query` 仅用于检索和工具调用，并保留原始问题与来源消息 ID，便于 Trace 复现。
- 高风险写操作继续拒绝或进入审批，不因上下文中曾出现某个参数而自动执行。
- 多任务执行记录每个 `task_id` 的状态；一个任务失败或拒绝不能让其他任务静默消失。
- 语义低置信度只增加澄清，不关闭 LLM；Provider 断路器只统计超时、429、5xx 和无效响应。

## 11. 前端体验

工作台按实际路由显示简短状态：

- `基于会话上下文`；
- `已检索知识库`；
- `已调用制造数据`；
- `已查询受控外部资料`。

只有 RAG、证据复用或工具路由显示相应证据抽屉；历史回顾和普通聊天不展示空证据区。SSE `stage` 事件
应反映真实步骤，例如“正在读取会话上下文”“正在检索知识库”，不能对未执行的检索显示假状态。

## 12. 验收用例

1. 同一线程先问业务问题，再问“我刚才问什么了”，准确返回上一条用户消息，Embedding 和 Reranker
   调用次数均为 0。
2. “把刚才回答简单解释一下”使用历史回答，不触发检索。
3. “它可能和 Recipe 有关吗”能引用上一轮对象，生成带来源槽位的 `standalone_query`。
4. “查询最新 SOP”必须重新检索，不能直接复用旧证据。
5. 页面刷新、API/Worker 重启后，同一线程仍可连续对话。
6. 新线程无法读取旧线程短期消息；不同用户无法读取彼此线程。
7. 长对话压缩后，最近消息仍可精确回忆，摘要边界可追踪。
8. 同一线程并发发送受到串行化或稳定冲突控制，消息、`turn_seq` 和摘要不乱序。
9. 上轮证据过期、被替代或当前用户无权时，`reuse_evidence` 被拒绝并重新检索或澄清。
10. 桌面和 `390 x 844` 移动视口亲自点击历史回顾、上下文承接、知识检索和工具场景；路由标签正确，
    页面无重叠、横向溢出和控制台错误。
11. “你好，顺便查一下 ETCH-03 报警”识别为 `mixed`，保留问候且执行查询；“回答太复杂了”识别为
    `feedback`，不触发投诉、Embedding 或 Reranker。
12. “查最近 24 小时 FDC，再对照当前 SOP 给排查建议”拆成不超过 3 个任务并合并为
    `rag_and_tool`，每项都有完成状态；不得漏掉后半句。
13. “查报警、修改 Recipe、生成报告”允许查询和安全的报告任务，Recipe 写操作单独拒绝或转审批，
    不能因为一个任务越权就丢弃其他任务。
14. “不是 ETCH-03，是 ETCH-04”纠正 Tool，并使旧 Chamber、Recipe 和证据复用资格失效；无关的
    Product 保留。
15. “别查了”只取消当前检索或待执行任务，不删除线程；“停止生成”继续沿用 T9-4.2 取消契约。
16. OOD 和非任务样本区分处理：感谢、翻译上一轮等合法会话可回答；危险、越权或明确超出产品能力的
    请求才拒绝。

现有 `semikb-intent-v1/v2` 保留原内容和 Hash，继续作为历史回归基线。T9-4.3.3 新增相互隔离的
`intent-example-bank-v1` 与冻结 `semikb-intent-v3`：示例库只服务 Few-shot，评估集不得进入示例检索，
防止测试泄漏。v3 重点补充真实失败表达、同对象不同动作、同动作不同对象、连续历史元问题、复杂混合任务
和困难负例。

评估范围继续覆盖 SOP 当前/历史版本、
Recipe 查询/影响分析、FDC 报警查询/含义解释、历史回顾、任务/非任务/混合输入、情绪干扰、多任务、
指代、省略、纠正、取消、中英文混合实体、越权写操作和 OOD。后续只从经过人工复核的失败 Trace 中扩充。

单意图指标增加逐类 Precision/Recall/F1、Macro/Micro-F1、混淆矩阵和高风险类别 F-beta；多任务指标增加
任务集合完全匹配率、漏任务率、多识别率、`target_type + action` 联合准确率、槽位操作准确率、依赖关系
准确率和最终路由计划准确率。原有不必要检索率、错误证据复用率、错误澄清率和危险工具调用率继续保留。
必须直接从原始多意图输入评估完整 `task_items`，不能先人工拆句后忽略拆分错误。

Few-shot 采用四组离线影子实验：A 为当前无意图卡的结构化 Prompt，B 为全量意图卡但不追加案例，C 为
全量意图卡加固定 Few-shot，D 为全量意图卡加从独立示例库动态检索的 Few-shot。四组使用相同冻结 v3，
记录质量、Provider 调用、活动卡数量、输入 Token、P50/P95 延迟和成本。3.3b 实测中 C 因意图卡
Macro-F1 回退未获候选资格；动态检索只有在多任务
精确匹配与关键混淆对上优于固定 Few-shot、危险任务 Recall 不回退且用户再次确认后才能进入在线链路；
本轮 D 在前两项均只与 C 持平，因此线上保留 B，不增加意图示例 Embedding 调用。
