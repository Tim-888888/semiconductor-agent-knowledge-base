## 2. 运行时闭环

下架严格按以下顺序执行：

1. 校验角色、Scope、revision 状态、原因和幂等请求 ID。
2. MongoDB 把 Document、Chunk、图片和表格置为 `withdrawn`，资产接口和检索 Repository 立即拒绝。
3. Worker 按稳定 Chunk ID 删除活动 Milvus 物理 Collection 中的投影，并用 Strong Consistency 读回确认。
4. 删除成功后写入 `withdrawn` 操作终态；失败时保持 MongoDB 阻断，并进入 `compensation_required`。

恢复先校验 `withdrawn`、审批、有效期、权限、原件及资产 SHA-256、Source Manifest 和活动索引版本，
然后重新编码并按 `staged -> published` 两阶段写入 Milvus，最后恢复 MongoDB 发布态。任何恢复失败都会
重新阻断，不能留下可检索的半恢复内容。MinIO 对象只读保留，全程不删除。

检索层增加防御性 MongoDB 生命周期/审批过滤。即使 Milvus 删除失败或出现陈旧向量，已下架 revision
仍不会被返回。DemoStore 同样禁止管理员绕过生命周期、审批和有效期门禁。

Worker 执行前使用 MongoDB 原子占用字段认领操作；同一 Celery task id 可在 Worker 丢失后继续执行，
其他重复投递只能读取当前状态，不能并发重建或发布同一 revision。`execution_id` 只属于 Repository 内部，
反序列化时会被剥离，不进入公共 Pydantic、OpenAPI、Trace 或前端契约。

## 3. API 与权限

新增接口均使用 `/api/v1`：

| 方法 | 路径 | 权限 |
| --- | --- | --- |
| `GET` | `/knowledge-documents` | `knowledge_admin/admin` |
| `GET` | `/knowledge-documents/{document_id}/revisions` | `knowledge_admin/admin` |
| `POST` | `/knowledge-documents/{document_id}/revisions/{revision}/withdraw` | `knowledge_admin/admin` |
| `POST` | `/knowledge-documents/{document_id}/revisions/{revision}/restore` | `knowledge_admin/admin` |
| `GET` | `/knowledge-document-operations/{operation_id}` | 操作发起人或 `admin` |
| `POST` | `/knowledge-document-operations/{operation_id}/retry` | 操作发起人或 `admin` |

操作返回 HTTP 202。`request_id`、actor、原因、前后状态、影响对象数、补偿状态和审计 ID 持久化到
MongoDB。相同请求内容重放复用原操作；同一 `request_id` 修改原因、动作或 revision 返回 409。

## 4. MongoDB 迁移

迁移版本为 `t9-4.4.6b-lifecycle-operations-v1`，只为
`document_lifecycle_operations` 创建以下四个索引：

- `operation_id`：唯一；
- `request_id`：唯一；
- `document_revision_created_at`：文档 revision 操作时间线；
- `status_updated_at`：补偿和任务轮询。

ECS 首次 dry-run 只有 4 个 `create`，没有 `drop`、`replace` 或数据改写；正式应用成功后第二次
dry-run 为 `actions=[]`。回滚只删除本迁移新增的索引；若迁移新建的 Collection 已有业务记录，则拒绝
删除 Collection。

MongoDB、Milvus、MinIO 和 Redis 全部通过，应用日志未发现 Traceback、异常、密钥模式或严重错误。
