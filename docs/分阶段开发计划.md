# 分阶段开发计划

## 执行原则

每个 Task 完成后必须更新 `开发记录.md`，运行对应测试，并以英文 Git commit
提交。真实服务配置、密钥和生产数据不进入 Git。

| Task | 目标 | 输入 | 输出 | 验收 |
| --- | --- | --- | --- | --- |
| T1 | 工程骨架 | 已确认技术选型 | 独立仓库、配置、文档、测试入口 | `.env` 已忽略，API/Web 骨架可启动 |
| T2 | 存储契约 | `.env` 服务参数 | Collection/Bucket/客户端烟雾检查 | 不泄露密钥，连接失败可诊断 |
| T3 | 演示数据 | 半导体模拟场景 | SOP、Recipe、Case、图片、黄金集 | 每条数据可追溯且带版本/权限 |
| T4 | 入库 | 原始文档和元数据 | Job、Chunk、资产、暂存发布 | 幂等重试，失败不发布 |
| T5 | 检索 | 已发布 Chunk | 混合召回、精排、图片引用 | 无权/过期内容不可返回 |
| T6 | 对话 | 检索与模拟工具 | 连续线程、追问、证据账本 | 同一线程可恢复，缺信息不猜测 |
| T7 | 运营能力 | Trace 与黄金集 | 入库中心、评估运行、基线对比 | 过程可重现 |
| T8 | Web UI | 稳定 API | 工作台、证据、Trace、评估页 | 四项产品亮点可操作 |
| T9 | 部署验收 | 已填 `.env` 和服务版本 | Docker、兼容矩阵、演示脚本 | 端到端 Demo 可重复 |

`T2` 与 `T3` 可并行。`T4 -> T5 -> T6` 为主链，`T7` 在 T4/T5 后并行，T8
等待 API 契约稳定后实施。

### T9-4 执行顺序

`T9-4` 严格按以下顺序执行，前一项未验收不得跳到后一项：

1. `T9-4.1` 流式能力探测与契约冻结：验证主备 LLM 的真实流式接口，冻结 SSE 事件、错误、取消和最终持久化语义。
2. `T9-4.2` SSE 全链路开发：FastAPI `StreamingResponse`、LangGraph 阶段事件、LLM Token Delta、
   `fetch + ReadableStream`、Nginx 禁止缓冲和兼容旧非流式接口。
3. `T9-4.3` 完整业务闭环：从用户上传 Markdown/PDF 开始，点击验证入库、连续问答、图片、Trace 和异步评估。
4. `T9-4.4` Provider 韧性：验证 Embedding、Reranker、LLM、MinerU、Web MCP 的超时、429、重试、降级和审计。
5. `T9-4.5` 容量与运行韧性：执行受控并发、资源峰值、磁盘/日志、容器重启、断连恢复和 OOM 边界测试。
6. `T9-4.6` 冷备恢复：备份后恢复到独立空目录，核对三类业务存储、Checkpoint、任务和检索结果，不覆盖当前数据目录。
7. `T9-4.7` 安全与可迁移部署：复核端口、鉴权、权限、短时图片链接、日志脱敏和镜像离线迁移产物。
8. `T9-4.8` 最终演示验收：运行自动脚本并亲自在桌面/移动浏览器完成点击、流式时序和截图验收，形成最终报告。

流式实现固定使用 `SSE + fetch ReadableStream`。服务端事件至少包括 `accepted`、`stage`、
`evidence`、`answer_delta`、`completed`、`error` 和 `heartbeat`；只输出可公开的处理阶段与答案，
不得输出隐藏推理、系统提示词或密钥。原有非流式消息接口保留用于兼容和回归测试。

T9-1/T9-2 完成不代表 T9 完成。标准门禁要求安全组新增 `80/tcp`、将 `22/tcp` 限制为用户公网 IP、
删除公网 `3389`，并保持所有数据库和存储端口不开放。当前测试 ECS 已新增 `80/tcp` 并删除公网
`3389`；考虑用户需要从不同办公地点连接，用户明确批准测试期暂时保留 `22/tcp` 对 `0.0.0.0/0`
开放。该项记录为限时风险例外，不视为生产安全标准已满足；正式发布前必须改为密钥登录并限制来源，
或接入受控运维通道。T9-3 完成不代表 T9 完成；T9-4 未通过前不得把部署烟雾验证写成完整端到端验收。
