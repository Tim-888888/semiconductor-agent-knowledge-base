# T9-4.6 容量与运行韧性验收

## 1. 验收结论

T9-4.6 已于 2026-08-23 在阿里云测试 ECS 上完成。面试 Demo 初始负载按 `1 -> 2 -> 3`
并发逐级执行，同时运行 1 个知识入库任务和 1 个 Full 离线评估，Celery Worker 固定
`--concurrency=1`。本轮结果如下：

- 6/6 个在线会话完成，HTTP 5xx、超时和业务错误均为 0。
- 入库任务发布成功，Full 评估 8/8 个 Case 执行完成。
- 断开流式连接后，请求被取消；同一线程随后可继续对话。
- 九个服务完成两轮受控顺序重启，重启后 API、Worker、Web、Redis、MongoDB、Milvus、
  两个 MinIO 和 etcd 均恢复。
- MongoDB 关键集合计数、Milvus Strong 逻辑行数、MinIO 对象数和 Redis 队列状态在稳定重启
  前后完全一致。
- 运行期间无 OOM、无意外重启；4 vCPU/8 GiB 可承载当前 Demo 档位。
- 公网工作台的真实 SSE、刷新恢复、桌面和 `390 x 844` 移动端显示通过，Console 0 error/warning。

T9-4.6 完成不代表 T9-4 或 T9 完成。下一阶段仍是 T9-4.7 冷备恢复，必须由用户明确发出
开始开发指令后才能实施。

## 2. 实现范围

本阶段新增四类可重复执行的受控验收工具：

1. `scripts/verify_t946_capacity.py`
   - 使用真实登录会话调用公网同源 API。
   - 在线负载只允许 `1 -> 2 -> 3` 有界并发，不允许无上限压测远程 Provider。
   - 记录 SSE accepted、首 Delta、总耗时、Route、Trace、检索耗时和 Provider 尝试数。
   - 并行触发一个幂等入库任务和一个 Full 评估，并等待其进入终态。
   - 断开一个 SSE 请求，先等待服务端自动取消；必要时调用与前端相同的取消 API，再验证同线程恢复。
2. `scripts/deployment/sample_t946_runtime.sh`
   - 周期采集宿主机内存、Swap、根盘、Load，以及所有项目容器的 CPU、内存和 PID。
   - 收到 TERM/INT 时仍写入结束快照，避免采样证据丢失。
3. `scripts/summarize_t946_runtime.py`
   - 将原始采样归并为宿主机和各容器峰值摘要。
4. `scripts/verify_t946_state.py` 与 `scripts/deployment/restart_t946_services.sh`
   - 前者对 MongoDB、Milvus、MinIO、Redis 建立重启前后状态快照；Milvus 使用 Strong consistency
     的 `count(*)`，避免物理统计延迟或 Tombstone/Compaction 干扰业务一致性判断。
   - 后者逐个重启服务并等待真实健康条件；每完成一个服务都再次检查整个栈，无健康检查的 Worker
     使用 Celery ping 验证，不把“容器运行中”冒充业务健康。

生产入库存储同时补齐 `record_provider_attempts` 转发，确保容量验收中的真实入库任务能够把
Embedding Provider 尝试记录到 MongoDB，而不是在发布前因适配层缺失接口失败。

## 3. 负载模型

```text
有界在线会话                    后台任务

Level 1: 1 个 SOP 问答          1 个 Markdown 入库
          |
Level 2: 1 个 SOP + 1 个组合任务 1 个 Full 评估（8 Case）
          |
Level 3: 1 个 SOP + 1 个组合任务 + 1 个图片检索
          |
          +---- 统一记录 SSE / Trace / Provider / 错误

Celery Worker: concurrency=1，入库与评估排队执行
宿主机采样: CPU / 内存 / Load / 磁盘 / Swap
容器采样: CPU / 内存 / PID / Restart / OOM
```

该档位用于证明 Demo 并发和后台队列可稳定共存，不用于推导生产容量上限。在线模型、Embedding 和
Reranker 都是远程 Provider，继续扩大压测会增加不可控调用量，必须另行设计压测预算和限流方案。

接近上限，因此不能把该时延解释为 ECS CPU/内存饱和，也不能为了降低时延关闭权限、证据或重排能力。

## 5. 断连、重启与数据一致性

### 5.1 SSE 断连

断连探针在收到 `accepted` 和 `stage` 后关闭连接。服务端请求最终状态为 `cancelled`；测试工具随后
使用真实前端取消 API 完成兜底，并在相同 `thread_id` 上发送恢复消息，结果为 `completed` 且路由为
`chat_direct`。这证明断连不会永久占用线程，也不会要求删除会话才能继续。

### 5.2 受控重启

九个服务按应用层到数据层的受控顺序逐个重启。每个服务恢复后都检查：

- 有 Docker Healthcheck 的服务必须达到 `healthy`。
- Worker 必须对 `celery inspect ping` 返回 `pong`。
- 全栈所有容器必须保持 running，且 `OOMKilled=false`。
- 完成整轮后重新运行真实 SSE 问答烟雾。

验收过程中先发现并修复三项验收脚本自身问题：无 Health 字段解析、无 `Config.Healthcheck` 字段解析，
以及 `set -o pipefail` 与 `grep -q` 组合导致的 SIGPIPE 假失败。修复后完整顺序重启连续通过两轮。

### 5.3 存储对账

稳定重启前后的关键状态完全一致：

| 存储 | 核验结果 |
| --- | --- |
| MongoDB | 12 个关键集合计数一致，包括 44 个 Document、154 个 Chunk、2199 个 Checkpoint |
| Milvus | Active Alias 均指向 `semikb_chunks_v4`，Strong 逻辑行数均为 149 |
| MinIO | `semikb-raw=56`、`semikb-derived=91`，前后一致 |
| Redis | PING 成功，Celery 队列深度为 0 |

第一次诊断曾看到 Milvus 物理统计从 148 变为 150。进一步使用 Strong `count(*)` 检查得到稳定逻辑
行数 149，确认这是物理统计、Tombstone 或 Compaction 时序，不是业务数据在重启中增删。状态核验器
因此固定使用逻辑强一致计数，避免把实现细节误报为数据丢失或重复。
