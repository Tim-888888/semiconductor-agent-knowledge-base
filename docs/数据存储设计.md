# 数据存储设计

## 职责边界

| 存储 | 权威内容 | 非职责 |
| --- | --- | --- |
| MongoDB | 文档 revision、Chunk 正文、权限、任务、线程、Trace、评估 | 向量相似度与文件二进制 |
| Milvus | Chunk 向量、检索过滤字段、索引版本 | 正文、图片、审批主数据 |
| MinIO | 原始文件、解析 Markdown、页面图、表格和真实图片 | 权限决策和长描述 |

## Milvus

物理 Collection 命名为 `semikb_chunks_v{index_version}`，查询使用
`semikb_chunks_active` alias。核心字段为 `chunk_id`、`dense_vector`、
`sparse_vector`、`document_id`、`revision`、`chunk_type`、`lifecycle`、审批/有效期字段、
Fab/Product/Tool/Chamber/Recipe 范围、`access_scope_key` 与 `index_version`。

向量维度由 `EMBEDDING_DIM` 固化到一次索引版本；不同 Embedding 空间不得混写。
`lifecycle` 用于把 `staged`、`published`、`quarantined` 和 `superseded` 数据隔离，检索只能
读取 `published`。T4 首次真实发布使用 `v2`，因为早期 `v1` 没有该字段；随后创建在线 Dense +
词法 Sparse 的 `v3`。确认 Provider 可原生返回 Sparse 后又创建 `v4`，先在物理 Collection 上完成
读回、自检索和 T5/T7 影子评估，才切换 Alias。`v2`、`v3` 均未删除，可用于受控回滚。

当前 `v4` 的 Dense 与 Sparse 由同一次 `qwen3.7-text-embedding` 在线请求返回。Dense 为 1024 维
并在客户端 L2 归一化；Sparse 保留 Provider 原始正权重，客户端校验非空、索引非负、值有限且无
重复索引。`index_releases` 和 Trace 同时记录 `dense&sparse`、Sparse Encoder 版本及
`dense_l2_sparse_provider_raw` 归一化契约。

## MinIO

```text
semikb-raw/documents/{document_id}/{revision}/source/{sha256}/{filename}
semikb-derived/documents/{document_id}/{revision}/parse/{parser_version}/{sha256}/document.md
semikb-derived/documents/{document_id}/{revision}/assets/{asset_id}/original.{ext}
semikb-derived/documents/{document_id}/{revision}/tables/{table_id}.html
```

两个 Bucket 均私有。对象仅保存短元数据：`document_id`、`revision`、`asset_id`、
`source_sha256`、`content_class` 和 `schema_version`。权限、图注、OCR 和检测结果
以 MongoDB 为准。

## MongoDB

一期 Collection：`document_catalog`、`chunk_catalog`、`image_assets`、
`ingestion_jobs`、`ingestion_job_events`、`index_releases`、`retrieval_traces`、
`evaluation_datasets`、`evaluation_runs`、`agent_threads`、`checkpoints`、
`checkpoint_writes`、`long_term_memories`、`audit_events`。

`evaluation_datasets` 以 `dataset_version` 唯一，保存规范化 Case 快照、SHA-256 `dataset_hash`、
来源与说明；同版本不同 Hash 拒绝覆盖。`evaluation_runs` 以 `evaluation_run_id` 唯一，保存
数据集 Hash、检索档位、参数/组件版本、Celery `worker_task_id`、状态、指标、Case 结果、
`trace_id`、失败标签和基线差异。API 和 Worker 都以 MongoDB 状态为准，Redis 结果不作为业务真相。

MongoDB 单机阶段不依赖跨 Collection 事务。MongoDB 是任务和业务状态真相，MinIO 是二进制
事实来源，Milvus 只保存可重建的检索投影。发布流程为：

1. 原件写入 MinIO，MongoDB 原子创建或复用幂等 Job，并持久化可重放输入。
2. 解析件和图片写入 MinIO，Document/Chunk/Image 以 `staged` 写入 MongoDB，向量以
   `staged` 写入 Milvus 并立即读回校验。
3. 质量门禁通过后，MongoDB 和 Milvus 切到 `published`，再切换活动 Alias、登记
   `index_releases` 并处理被替代版本。
4. 任一步失败都把本 Revision 置为 `quarantined` 并按精确 Chunk ID 删除向量；活动索引
   已有成功发布记录时，单文档失败只记录 `last_failure_at`，不会把整个索引误标成失败。

`ingestion_jobs.events` 是单机 MongoDB 阶段的权威事件时间线，`ingestion_job_events` 以
`event_id` 幂等镜像，供任务中心分页和审计查询。Redis/Celery 只负责投递和执行，不是任务
状态真相。

### T6 会话与记忆结构

- `agent_threads`：业务线程目录，保存 `thread_id`、JWT Scope、状态、摘要和展示消息；不替代图状态。
- `checkpoints` / `checkpoint_writes`：只由官方 `MongoDBSaver` 管理。唯一键分别为
  `(thread_id, checkpoint_ns, checkpoint_id desc)` 和
  `(thread_id, checkpoint_ns, checkpoint_id desc, task_id, idx)`，业务代码不得直接拼写状态文档。
- `long_term_memories`：由 LangGraph MongoDB Store 管理物理键 `(namespace_str, key)`；
  `value` 内保存 `memory_id`、类型、内容、Scope、来源、置信度、审批与过期时间。
- `audit_events`：`event_id` 唯一并以 upsert 追加；Agent 完成事件和每次只读工具调用分别记录，
  不保存模型内部思维过程或密钥。

现有项目从早期占位索引升级时使用 `python -m semikb.storage.t6_mongo_migration`。命令默认
dry-run，只允许 `semikb` 数据库和上述 4 个空 Collection，保存本地快照后才可显式 `--apply`；
异常会恢复原索引。MongoDB 单机可满足一期演示持久化，但不具备生产高可用和跨 Collection 事务保证。
