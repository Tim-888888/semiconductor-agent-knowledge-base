# T9-4.5.1 通用澄清状态机与多轮槽位闭环修复计划

## 1. 状态与目标

- 状态：已编排，未开始开发。
- 前置：T9-4.5 已完成。
- 后置门禁：T9-4.5.1 未验收前不得进入 T9-4.6。
- 开发门禁：只有用户明确发出开始开发指令后才能修改业务代码或部署。

本工作包修复的是一类澄清闭环缺陷，而不是为“看制造数据”等已知句子增加特判。系统必须把
LLM 给出的候选意图和任务转换为服务端可验证的澄清状态，在后续回答中更新结构化状态，并证明
每轮澄清取得进展或以明确原因安全停止。

## 2. 已确认的缺陷类别

1. `clarify` 路由可能没有可填写的缺失槽位，图节点随后生成不在正式槽位注册表中的临时字段。
2. 用户已经完成目标消歧或补充部分槽位时，系统可能只拼接文本，没有关闭对应待解决项。
3. LLM 的任务级 `execution_policy=clarify`、候选业务路由和服务端缺失槽位计算之间可能失配。
4. 连续两轮可能产生相同澄清签名，直到达到轮数上限，没有“是否取得进展”的约束。
5. 用户修改目标或纠正槽位时，旧任务、依赖槽位和证据可能没有按依赖关系失效。
6. 内部字段名、原因码或任务实现细节可能泄露到用户回复和前端任务区域。

## 3. 设计原则

- LLM 负责语义候选和自然表达；服务端负责允许的澄清类型、槽位、路由、权限和状态迁移。
- 不为来源、已知问题、固定答案或单句表达建立专用分支；未知未来输入走同一状态机。
- 原问题与补充回答分别保留；不再把字符串拼接结果作为唯一状态真相。
- `route=clarify` 必须对应一个可执行的 `ClarificationFrame`，不能存在无目标澄清。
- 每轮必须记录 `pending_before`、`resolved_by_answer`、`pending_after` 和 `made_progress`。
- 保持现有最多两轮澄清的安全上限；第二轮只追问剩余项，无进展时给出可理解的安全结束说明。
- 澄清期间不得提前调用 Retrieval、Embedding、Reranker、制造数据工具或 Web。
- 不新增基础设施、模型或第二次意图理解调用；复用现有结构化理解、Checkpoint 和自然回复网关。

## 4. 版本化状态契约

新增版本化 `semikb-clarification-frame-v1`，至少包含：

| 字段 | 含义 |
| --- | --- |
| `frame_id/schema_version` | 稳定标识和契约版本 |
| `kind` | `intent_disambiguation`、`slot_collection`、`history_reference` 或 `control_confirmation` |
| `original_request` | 原始用户任务，不被补充文本覆盖 |
| `candidate_route/task_ids` | 服务端允许继续处理的候选路由和任务 |
| `pending_items` | 待解决的正式槽位或受控枚举项 |
| `resolved_items` | 已通过当前或前序补充验证的项目及来源消息 ID |
| `allowed_values` | 仅用于枚举型消歧；槽位型问题不伪造候选值 |
| `round/no_progress_count` | 有界轮次和无进展计数 |
| `signature` | 由类型、待解决项和候选任务生成，用于阻止原样重复提问 |

正式业务槽位仍由统一注册表管理。目标消歧使用受控枚举，不伪装成 `request_goal` 一类普通槽位。
Checkpoint 保存完整 Frame；`agent_threads` 继续保存前端所需的最小投影。新增审计字段必须可选且有默认值，
旧 MongoDB 文档、旧 Trace 和旧 Checkpoint 仍可读取。

## 5. 服务端处理流程

```text
用户输入
  -> 一次结构化理解：候选意图、任务、显式/继承槽位、置信度
  -> RoutePolicy 依据任务类型和槽位注册表计算候选业务路由
  -> 服务端计算真实缺失条件
       -> 信息完整：执行既有 direct/RAG/tool/web 路由
       -> 目标确实歧义：创建 intent_disambiguation Frame
       -> 业务槽位缺失：创建 slot_collection Frame
       -> 历史目标缺失：创建 history_reference Frame
  -> 生成自然澄清气泡并 interrupt
  -> 用户补充
  -> 结合 Frame 解析本轮答案
  -> 校验枚举、实体 Grounding、权限和槽位依赖
  -> 更新 resolved/pending，计算 made_progress
       -> pending 为空：重新运行确定性路由并执行
       -> 有进展但仍缺项：只追问 pending_after
       -> 用户修改目标/槽位：更新状态并失效依赖项
       -> 无进展且仍可追问：给出更具体的合法选项或字段说明
       -> 达到上限：安全结束并使用用户可理解的字段名称
```

`RoutePolicy` 不直接接受 LLM 的 `execution_policy=clarify` 作为完整决定。模型要求澄清但没有合法原因时，
服务端必须从任务的候选路由推导真实缺失槽位；仍无法推导时才能建立受控目标消歧 Frame。

## 6. 兼容与非回归护栏

1. 开发前先冻结当前行为和调用计数，建立此次线上缺陷的特征测试，但不把该句子写成生产规则。
2. 新逻辑置于版本化开关后，先在测试和离线影子模式对比旧/新决策，再在 ECS 启用；关闭开关即可回滚。
3. 旧 Checkpoint 中没有 Frame 或仍带旧临时字段时，通过兼容适配器重新推导合法 Frame，不修改历史消息。
4. 不修改冻结的 `semikb-intent-v1/v2/v3` 内容或 Hash；新增独立多轮澄清评估集，禁止从评估句子生成特判。
5. `chat_direct`、历史回顾/变换、反馈、取消、拒绝、`internal_rag`、`tool_only`、`rag_and_tool`、
   `rag_and_web` 和 `reuse_evidence` 均保留现有路由契约及展示模式。
6. 澄清和拒绝仍显示普通气泡；RAG/工具类完成结果仍显示结构化卡片。刷新和恢复不得改变历史消息展示。
7. 不改变 ACL、版本过滤、证据账本、三类存储模型、Provider 重试、入库发布或评估数据分层。

| 子任务 | 输入 | 输出 | 验收 |
| --- | --- | --- | --- |
| 5.1-A 影响面审计与特征测试 | 当前代码、线上脱敏审计、现有测试 | 调用图、旧行为基线、失败用例和影响清单 | 先复现后修改；确认无数据迁移和下游调用 |
| 5.1-B Frame/审计兼容契约 | 槽位注册表、Checkpoint、Mongo 契约 | 版本化 Frame、可选审计、旧数据适配器 | 旧文档/Trace/Checkpoint 可读；Schema 向后兼容 |
| 5.1-C 解析器与 RoutePolicy | 结构化理解、候选任务和 Frame | 通用回答解析、缺失条件推导、进展校验 | 无非法槽位；相同签名不得连续出现；无单句特判 |
| 5.1-D LangGraph 闭环 | 新契约与既有 interrupt/resume | 结构化恢复、部分补充、纠正和安全结束 | 重启后可继续；补充只更新相关状态；最多两轮 |
| 5.1-E 展示与审计 | 路由结果和状态转换 | 自然气泡、用户字段名、脱敏 Transition Trace | 不泄露内部字段；历史卡片和直接回答不回归 |
| 5.1-F 自动化非回归 | 新多轮集、冻结意图集、现有全量测试 | 单元/集成/属性化/冻结回归报告 | 全量基线不下降；澄清期间全部下游增量为 0 |
| 5.1-G ECS 与浏览器验收 | 已通过自动门禁的镜像 | 真 Mongo Checkpoint、桌面/移动点击和证据 | 只更新 API/Worker/Web；数据容器 ID 不变；回滚开关实测 |

必须严格按 A 到 G 执行。任一公共契约变化超出可选字段和兼容适配器范围时，停止开发并先说明迁移影响。

## 8. 测试矩阵

- 一次补齐、分两轮补齐、乱序补齐、只补充部分字段。
- 枚举原词、自然同义表达、否定、纠正、清除和从数据查询切换到知识查询。
- 无关回答、“不知道”、重复回答、冲突回答和 Prompt 注入。
- LLM 返回 `clarify` 但没有 `missing_slots`、返回非法槽位、返回不允许的目标或低置信度。
- 同线程恢复、服务重建恢复、旧 Checkpoint 恢复、请求重放和并发写入。
- 普通聊天、连续历史回顾、历史简化、能力咨询、反馈、取消、拒绝及多任务组合完整回归。
- RAG、工具、Web、图片、Trace、SSE、Provider fallback 和消息展示完整回归。

新增指标至少包括：澄清完成率、重复澄清率、无进展轮次占比、澄清后错误路由率、平均澄清轮数、
内部字段泄露率，以及信息未补齐时的下游误调用率。

## 9. 完成门禁

- 所有 `clarify` 结果都有合法 Frame，非法/临时槽位产生率为 0。
- 受控测试中连续相同澄清签名产生率为 0；部分回答后只追问剩余项。
- 用户明确选择合法目标后，目标消歧在本轮关闭，不再次询问同一目标。
- 未补齐时 Retrieval、Embedding、Reranker、Tool、Web 调用增量均为 0。
- 原有全量后端测试、Ruff、前端 lint/build、凭据扫描和冻结意图评估全部通过且关键指标不下降。
- ECS 只替换应用容器，MongoDB、Milvus、双 MinIO、etcd、Redis 容器 ID 不变。
- 公网工作台完成多种未知措辞、部分补充、纠正、无进展、刷新恢复和桌面/移动验收。
- 验收报告、开发记录和英文 Git commit 完成后，T9-4.5.1 才能标记完成并解除 T9-4.6 门禁。
