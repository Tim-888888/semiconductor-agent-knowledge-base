# T9-4.4.1 Knowhere 上游与契约审计

## 1. 结论

T9-4.4.1 固定 Knowhere 官方仓库 `main` 在提交
`2e4eb5846249d273b11902ee00f26db949e45b38`，提交时间为
`2026-08-14T23:14:13+08:00`，许可证为 Apache-2.0。本阶段只做源码、许可证、依赖和契约审计，
没有把 Knowhere 源码复制进本项目，也没有修改运行时代码、依赖、镜像、ECS 或存储数据。

审计确认：Knowhere 的格式路由与结构恢复思路适合复用，但它的 `pandas.DataFrame` 输出、Worker、
PostgreSQL/S3、任务状态、全局配置和 LLM 调用不能成为本项目业务契约。后续以本项目自己的
`semikb_ingest` 为边界，只吸收必要算法和格式处理经验。

## 3. 上游真实能力与边界

上游 README 与代码存在不能忽略的差异，因此本项目以固定 Commit 的源码和测试为准，而不是只看
“Supported Formats”文字：

| 格式 | README | 固定源码事实 | 本项目决定 |
| --- | --- | --- | --- |
| PDF | 支持 | 独立 PDF 适配器，传统路径趋于弃用，推荐 page-memory；MinerU 是 PDF Provider | 保留现有远程 MinerU PDF 适配器，不引入 page-memory 重依赖 |
| DOCX | 支持 | 独立 DOCX 解析器，处理段落、表格、图片和标题层级 | 参考其文档顺序与资产累积方式，自主输出本项目模型 |
| XLSX | 支持 | `openpyxl + pandas` 专用解析，默认排除隐藏 Sheet | 参考子表和合并单元格逻辑，使用 `openpyxl` 输出本项目模型 |
| CSV | README 声称支持 | `format_router.py` 没有 `.csv` 路由 | 使用 Python 标准库自主实现，不继承不存在的上游能力 |
| PPTX | 支持 | 独立适配器，但推荐转 PDF/page-memory，涉及 LibreOffice 或远程转换 | 首期用 `python-pptx` 直接恢复页、文本框、表格和图片，不装 LibreOffice |
| 图片 | 支持 | 独立 VLM/OCR 管线，和上游 LLM/配置/DataFrame 深度耦合 | 参考分类、OCR、图注和感知哈希思路，使用本项目 Provider |
| Markdown/TXT | 支持 | 独立解析器，但依赖上游标题、表格、摘要和 DataFrame 管线 | 保留轻量本地实现并增强结构，不复制整条上游管线 |
| HTML | README 标为 Coming Soon | 源码已有 `.html/.htm` 路由和契约测试 | 作为首期受控格式，自主净化脚本、样式和导航噪声 |
| JSON | README 和路由均列出 | `JsonParseAdapter` 返回 `parsed_df=None` | 首期明确不支持，不能把空适配器包装成已实现 |
| DOC/XLS | 路由支持 | 先调用 LibreOffice 转换为 DOCX/XLSX | 首期不支持，避免引入系统级 Office 运行时 |

Knowhere 当前 `resolve_document_format()` 主要按扩展名判断。本项目必须同时校验扩展名、声明 MIME、
文件签名和 Office ZIP 必需成员，发生冲突时失败，不能由扩展名覆盖真实文件类型。

当前项目的真实实现仍是简化路径：`rag_ingestion/service.py` 只把 Markdown/TXT 直读，其他后缀统一
调用 `MinerUPrecisionClient`；API 注释也把二进制格式统一描述为 MinerU，前端文件选择器则已经展示
PDF、DOCX、XLSX 和图片。这个 UI/后端能力差异必须由 T9-4.4.2~T9-4.4.5 闭合，不能用文件选择成功
证明专用解析已经存在。

## 5. `semikb_ingest` 冻结契约

机器可读 Schema 位于
[`semikb-ingest-contract-v1.schema.json`](evidence/t9-4-4-1/semikb-ingest-contract-v1.schema.json)，
契约版本固定为 `semikb-ingest-v1`，根输出为 `ParsedDocument`：

```text
ParsedDocument
  + contract_version / source_format / normalized_markdown
  + chunks: ChunkDraft[]
  + images: ImageAssetDraft[]
  + tables: TableAssetDraft[]
  + provenance: ParseProvenance
  + warnings: ParseWarning[]
  + metrics: ParseMetrics
```

- `ChunkDraft` 保存文本、Chunk 类型、标题路径、页/Slide/Sheet/Cell 等来源位置、父子关系和资产 ID。
- `ImageAssetDraft` 保存真实二进制的进程内句柄、SHA-256、图注/OCR/检测结果、置信度和来源位置。
- `TableAssetDraft` 保存 HTML、Markdown、列头、行列数量、来源位置和关联 Chunk。
- `ParseProvenance` 强制记录 Parser/Provider 版本、Knowhere Commit、源文件 MIME/SHA-256 和检测格式。
- `BinaryPayload.handle` 只是在同一 Worker 进程内交接二进制的临时句柄；它不能写入 MongoDB、
  Milvus、Trace 或成为 MinIO 对象路径。`rag_ingestion` 消费后按现有权限路径写入 MinIO。

解析包不接收或决定审批状态、有效期、Fab、Product、Tool、Chamber、Recipe、访问权限或索引版本；
这些仍由现有受控入库层补齐并校验。

## 6. 稳定错误码

完整目录位于
[`semikb-ingest-errors-v1.json`](evidence/t9-4-4-1/semikb-ingest-errors-v1.json)。错误按
`validating -> parsing -> quality_check` 分层，并为每项冻结 HTTP 状态、重试策略和隔离要求。

主要类别包括：

- 格式与安全：`INGEST_UNSUPPORTED_FORMAT`、`INGEST_FILE_TYPE_MISMATCH`、
  `INGEST_INVALID_OFFICE_CONTAINER`、`INGEST_ZIP_BOMB_SUSPECTED`。
- 文件问题：`INGEST_CORRUPT_DOCUMENT`、`INGEST_ENCRYPTED_DOCUMENT`、
  `INGEST_TEXT_DECODE_FAILED`、`INGEST_DOCUMENT_LIMIT_EXCEEDED`。
- Provider：`INGEST_PARSER_NOT_CONFIGURED`、`INGEST_PARSER_UNAVAILABLE`、
  `INGEST_PARSER_TIMEOUT`。
- 输出门禁：`INGEST_PARSE_FAILED`、`INGEST_EMPTY_PARSE_RESULT`、
  `INGEST_ASSET_EXTRACTION_FAILED`、`INGEST_QUALITY_GATE_FAILED`、
  `INGEST_CONTRACT_VIOLATION`。

后续不得再用 `type(exc).__name__.upper()` 作为对外稳定错误码；内部异常只能映射到上述目录并记录脱敏
日志。该映射属于 T9-4.4.4，不在本阶段提前修改。

## 7. 格式路由冻结

[`format-capability-matrix-v1.json`](evidence/t9-4-4-1/format-capability-matrix-v1.json) 冻结首期九条路由：

```text
Markdown / TXT / HTML / PDF / DOCX / XLSX / CSV / PPTX / Image
```

只有 PDF 可以调用 MinerU。DOCX、XLSX、CSV、PPTX、HTML 和图片均有独立 Provider/Parser；未知格式
明确拒绝，格式内回退必须显式声明。DOC/XLS/JSON/XML/音视频等处于首期范围外。

安全门禁至少包括：OOXML ZIP 成员与解压限制、路径穿越、图片解压炸弹、HTML 外链禁用、隐藏 Sheet
默认排除、公式不执行、宏格式不接收、损坏/加密文档不发布。

## 8. 依赖、镜像和资源影响

当前项目没有本地 Office/图片结构解析依赖。T9-4.4.2 预计只评估并锁定以下轻量运行库，**本阶段尚未
安装**：

| 用途 | 候选依赖 | 上游固定版本 | 本项目策略 |
| --- | --- | --- | --- |
| DOCX | `python-docx` | 1.2.0 | Python 3.12 锁定测试后纳入 |
| XLSX | `openpyxl` | 3.1.2 | 不引入 Pandas，设置 Sheet/Cell 资源上限 |
| PPTX | `python-pptx` | 1.0.2 | 直接读取 OOXML，不调用 LibreOffice |
| 图片 | `Pillow` | 12.2.0 | 设置像素和尺寸上限，实际版本由锁文件兼容测试确定 |
| HTML | `beautifulsoup4`、`markdownify` | 4.13.4、1.2.2 | 禁止外链抓取，清除 script/style/导航噪声 |
| XML 基础 | `lxml` | 6.1.0 | 多数由 Office 包带入，锁定 wheel，不执行外部实体 |

明确不引入：Pandas、PyMuPDF/PyMuPDF4LLM、Tabula、OpenJDK、LibreOffice、MarkItDown、pptx2md、
Loguru、OSS2，以及 Knowhere 的 PostgreSQL/S3/Redis/Celery 业务依赖。因此无需新增容器、端口、数据库
或本地 GPU，也不要求把基础镜像从 Debian Bookworm 升到 Trixie。

当前 API/Worker 共用项目镜像，加入上述 wheel 会同时增加两类容器的镜像体积。T9-4.4.2 必须记录
修改前后压缩/展开镜像大小、构建时间和 Worker 空载内存；若需要系统包、新服务或本地模型，必须另行
取得用户确认。

直接图片解析还需要一个可生成图注/OCR 的 VLM 模型配置。计划复用现有 Qwen API 凭据，新增独立
模型名配置；若现有 Endpoint 不支持视觉输入，则在 T9-4.4.3 前由用户提供兼容 VLM Endpoint/模型名，
否则图片 Job 使用 `INGEST_PARSER_NOT_CONFIGURED` 明确失败，不能伪造图注。
