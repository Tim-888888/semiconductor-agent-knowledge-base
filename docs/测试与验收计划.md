| 范围 | 测试 | 通过标准 |

| 长期记忆 | 显式批准、用户隔离、TTL | 不自动沉淀对话；未批准或过期内容不进入上下文 |

| 部署制品 | 配置生成、Compose、网络、端口、镜像、资源和恢复门禁 | 不复制 SSH/旧地址；只有 80 发布；空目标才能恢复 |

## T4 真实存储验收

前置检查：

```powershell
conda run -n dl python -m semikb.storage.verifier
conda run -n dl python scripts/verify_t4_ingestion.py
```

验收脚本只使用 `T4-CASE-ETCH-03` 和 `T4-RETRY-SOP-ETCH-03` 两条 CC0 合成资料。它验证
当时的真实 BGE-M3 Dense/Sparse 编码、MinIO 原件/解析件/图片回读、MongoDB Job/Event/Catalog、
Milvus staged/published 生命周期、活动 Alias、失败后跨服务实例重试和重复提交幂等性。

2026-08-11 实测：2 个 Document、5 个 Chunk、1 个 Image、2 个 Job；一个 Job 在注入
Embedding 失败后第 2 次成功；20 条镜像事件与 Job 内事件一致；5 个 MinIO 对象可读取；
5 条 Milvus `v2` 记录均为 `published`；Alias 指向 `semikb_chunks_v2`。脚本连续执行两次，
Job ID、数据数量和尝试次数不变。

另以 `DEMO_MODE=false` 启动独立 Celery `solo` Worker，通过真实 Redis 投递并消费一条临时
合成 SOP，Worker 完成当时的 BGE-M3 和三存储发布。该测试同时发现并修复了 Celery App 未显式加载
任务模块的问题；自动测试会检查 `semikb.ingestion.process` 和 `semikb.ingestion.retry` 已注册。
临时验收数据和 Worker 进程在验证后已精确清理。

2026-08-12 当前基线已迁移为在线 `qwen3.7-text-embedding` 原生 Dense/Sparse，活动索引为
`semikb_chunks_v4`。迁移验收覆盖在线 API、候选构建、行读回、自检索、Alias 回滚保护、
发布前后 T5/T7 黄金集、跨 Worker 新文档入库和 T8 浏览器复验，详见
`docs/Qwen原生Sparse迁移验收.md`。

## T6 真实 Agent 验收

```powershell
conda run -n dl python -m semikb.storage.verifier
conda run -n dl python scripts/verify_t6_agent.py
```

脚本先提交缺少 Product、时间和 Tool 的良率问题，确认图经 `interrupt()` 暂停并写入 MongoDB；
然后重建 ConversationService，用同一 `thread_id` 和 `Command(resume=...)` 补充条件。完成路径必须
包含 T5 内部 Chunk、证据账本、引用、模拟只读制造工具、审计和显式批准长期记忆。脚本拒绝无内部
受控证据或声明“根因是”的结果，并在 `finally` 中按临时 ID 清理线程、Checkpoint、Trace、审计和记忆。

## 人工验收顺序

1. 从空 Demo 启动 API 和 Web，提交现行 SOP 问题。
2. 提问缺少 Product/时间/设备的良率问题，确认最多两次追问且未检索。
3. 检索边缘环状缺陷，打开证据抽屉中的合成晶圆图。
4. 查看 Trace 的过滤、Dense/Sparse、RRF、Rerank 和截断结果。
5. 新建训练文档，检查入库任务阶段事件和幂等重试。
6. 运行 `demo-v2`，确认正向证据与无权限、过期、无答案等负向 Case 可以追溯；`demo-v1` 只保留为历史基线。
7. 运行 `python scripts/verify_t5_retrieval.py`，比较 Dense、Dense+Sparse、Reranker、HyDE 四组真实基线，并验证无证据 Case。

填好 `.env` 后先运行 `python -m semikb.storage.preflight`。只有四个数据存储均显示
`connection verified`，才能开始真实资源的集成验收。T4、T5、T6 当前真实验收均已完成；
指标和回答只代表合成知识、公开资料及模拟制造数据场景。

## T9 部署验收

T9-2 本地执行 `tests/test_deployment_artifacts.py`、全量后端测试、Ruff、ESLint、Vite build 和使用临时
服务器 `.env` 的 `docker compose config --quiet`。本机 Docker Desktop Linux Engine 未运行时，
只能证明 Compose 可解析，不能宣称镜像可构建或服务已部署。

T9-3/T9-4 必须在新 ECS 继续完成：安全组复核、Moby/Compose 版本冻结、镜像拉取与构建、10 个容器
健康状态、只发布 80、空存储初始化、`--seed-demo` 幂等发布、浏览器四页点击、真实图片、连续线程、
Trace、异步评估、资源峰值和一次冷备恢复演练。任一项缺证据时 T9 保持未完成。

T9-4 新增流式对话门禁。后端使用 POST SSE，前端使用 `fetch` 读取 `ReadableStream`，不得用只能发起
GET 的原生 `EventSource` 替代当前带鉴权和请求体的消息接口。验收必须同时覆盖：

- `accepted -> stage -> evidence -> answer_delta -> completed` 正常路径，以及 `error`、`heartbeat`、
  `AbortController` 取消和网络断连后的线程状态对账。
- Nginx 关闭该路由的代理缓冲，使用 `curl -N` 和浏览器时间戳证明事件分批到达，不能把完整答案一次性吐出。
- SSE 建连后 1 秒内出现首个可见状态；超过 10 秒没有业务事件时发送心跳，避免页面无反馈。
- 完成事件返回数据库中的规范线程结果；失败时不把半截助手答案保存为最终消息；同一 `request_id`
  重试不得产生重复用户消息或助手消息。
- 桌面与 390 x 844 移动视口均亲自点击，检查长答案滚动、停止生成、切页/返回、控制台和无横向溢出。

其余 T9-4 验收包括 Provider 超时/429/降级、面试 Demo 负载下的 CPU/内存/磁盘/延迟与容器重启、
日志轮转、冷备恢复到独立空目录、端口/RBAC/短时图片链接/日志脱敏复核，以及可离线迁移的固定镜像清单
和 SHA-256。执行顺序、测试边界和证据清单见 `docs/T9-4端到端验收计划.md`。
