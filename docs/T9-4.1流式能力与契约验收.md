# T9-4.1 流式能力与契约验收

## 1. 范围与结论

本阶段只完成主备 LLM 流式能力探测和 SSE/幂等/持久化契约冻结，不新增消息路由，不修改前端，也不
改变当前非流式对话行为。SSE 全链路实现仍属于 T9-4.2。

2026-08-12，本地开发环境已分别和组合验证 CloseAI `gpt-5.6-luna`、DashScope `qwen-flash`。
两家均返回 OpenAI Chat Completions 风格的真实 `content` Delta，探测正文一致且 SHA-256 相同；
没有使用 fallback，也没有用完整答案拆分模拟流式输出。

## 2. Provider 实测证据

命令：

```powershell
conda run -n dl python scripts/verify_llm_streaming.py --provider all
```

脱敏结果：

| Provider | 请求/报告模型 | JSON 事件 | 可见 Delta | 首 Delta | 总耗时 | 终止方式 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| CloseAI | `gpt-5.6-luna` / `gpt-5.6-luna-2026-07-09` | 31 | 28 | 4963.94 ms | 5166.50 ms | `finish_reason=stop` 后正常 EOF |
| Qwen | `qwen-flash` / `qwen-flash` | 12 | 10 | 362.70 ms | 544.63 ms | `[DONE]` |

两次内容长度均为 114，SHA-256 均为
`2450fe513b71edd5bc2c804554c84cb5706313b695dbec39efb488abfea2fb46`。探测工具不输出原始正文、
API Key、Endpoint 或 reasoning 内容。Luna 的首 Delta 明显慢于 Qwen，但一旦开始生成就连续返回 28
个真实 Delta；这证明 T9-4.2 仍需要立即发送 `accepted/stage/heartbeat`，不能只等待模型首 Token。

首次严格探测曾因 Luna 不发送 `[DONE]` 被拒绝。复核事件后确认其具有 `finish_reason=stop` 并正常
关闭 SSE，因此冻结两种合法 Provider 终止：`done_marker` 和 `finish_reason_eof`。普通 EOF 且两者都
不存在时仍按残缺响应失败。

## 3. 已冻结的 SSE 契约

- 路由：`POST /api/v1/threads/{thread_id}/messages/stream`，由 T9-4.2 实现。
- 请求：`content + request_id`；客户端生成 `request_id` 并在同一次业务重试时复用。
- 事件：`accepted`、`stage`、`evidence`、`answer_delta`、`heartbeat`、`completed`、`error`。
- 顺序：`accepted` 必须第一，`sequence` 从 1 连续递增，`completed/error` 必须是最后一条。
- SSE：`id` 为事件 ID，`event` 为事件类型，`data` 为包含完整信封的单行 UTF-8 JSON。
- 最终结果：`completed.data.result` 使用同步接口共同的 `SendMessageResponse`。
- 可见性：只允许用户可见阶段、受权限过滤证据和答案文本；隐藏 reasoning 只计数、不传输、不持久化。

阶段枚举固定为约束分析、等待澄清、内部检索、外部搜索、重排序、答案生成、答案校验和结果持久化。
心跳是有序事件并占用 `sequence`，不携带业务内容。

## 4. 错误与取消语义

SSE 响应头发出前完成 JWT、Scope、请求体和 Thread 校验，失败返回普通 HTTP JSON。响应头发出后，
错误使用终止 `error` 事件，稳定错误码覆盖请求冲突/处理中、Provider 超时/限流/不可用、校验失败、
取消和内部错误。消息最长 500 字，只描述用户可执行动作，不包含 Endpoint、密钥、Prompt 或堆栈。

用户点击停止时，前端 `AbortController` 关闭连接，服务端取消下游调用并把请求记为 `cancelled`；意外
断连采用相同服务端语义。若最终结果已经持久化则不回滚；否则保留已经恰好一次写入的用户消息，不保存
半截助手答案。客户端重新进入线程后必须以 MongoDB 状态对账。

## 5. 幂等与最终持久化语义

T9-4.2 将按已冻结的 `AgentMessageRequestRecord` 建立 `agent_message_requests`：

1. 唯一键是 `(actor_user_id, thread_id, request_id)`；正文只存在于 Thread，台账保存 SHA-256。
2. 用户消息写入和请求占位完成后才能发送 `accepted`。
3. Stage、Evidence、Heartbeat 和 Delta 不作为最终 Thread 消息持久化。
4. 同一 ID/相同 Hash：运行中拒绝重复执行，已完成重放，失败/取消重试不重复追加用户消息。
5. 同一 ID/不同 Hash 返回 `request_conflict`。
6. 只有答案验证、助手消息、Checkpoint、Trace 关联和请求台账全部写入后才发送 `completed`。

MongoDB 当前为单机，无法依赖跨 Collection 事务。T9-4.2 必须使用原子 upsert、状态条件更新和补偿，
并用故障注入证明不会出现“已发送 completed 但最终答案未持久化”的状态。

## 6. 自动测试

新增测试覆盖：

- 请求 ID 和幂等台账模型。
- Pydantic 事件 discriminator、连续序号和终止事件位置。
